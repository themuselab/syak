# 샥 포트폴리오 개발 인계

2026-11-28 기준 설계안. 목표는 사용자가 마음에 드는 네일·헤어·메이크업 사진을 누르고, **같은 지점의 다른 작업을 본 뒤 해당 샵 상세와 예약 경로로 이동**하는 것이다. 현재 운영 중인 것은 수집·정제 파이프라인이다. 피드 조회 뷰와 인덱스를 시험한 뒤 운영 RDS에서 제거했고, 소비자 앱과 API도 배포하지 않았다.

## 다른 PC에서 시작하기

| 위치 | 담당 작업 |
|---|---|
| 기존 수집 Mac | 인스타 공개 피드 수집, 사진 선별, S3 저장, RDS 동기화, 네이버 플레이스·공공데이터 대조 및 개별 검토. 작업 큐와 브라우저 세션도 이 Mac에서 이어간다. |
| 다른 개발 PC | 이 문서로 데이터 계약을 확인하고 로컬 PostgreSQL·샘플 이미지로 API와 화면을 개발한다. 이 작업을 위해 두 번째 크롤러를 설치하거나 운영 DB·버킷 설정을 바꿀 필요가 없다. |

이 문서는 [themuselab/syak](https://github.com/themuselab/syak)에 있다. API와 DB 마이그레이션은 [themuselab/syak_BE](https://github.com/themuselab/syak_BE), 소비자 앱은 [themuselab/Syak_FE](https://github.com/themuselab/Syak_FE)에서 작업한다. 각 저장소의 기본 브랜치와 루트 `CLAUDE.md`를 확인한다. 백엔드의 `db/`와 `src/contexts/catalog/`, 앱의 `app/`, `src/screens/`, `src/shared/domain/`이 시작점이다. Git에서 가져올 인계물은 이 설계 문서다. 초기 시험 코드는 수집 Mac에 초안으로 보관돼 있다. 로컬 검증에는 운영 인증키나 Mac의 SQLite 사본이 필요하지 않다.

## 조회 모델 제안

운영 원본은 샵·사진·시술 판정 단위로 유지한다. 읽는 쪽에는 SQL 뷰 `catalog_portfolio_cards`를 통해 **한 행이 한 샵의 사진 한 장**이 되도록 제공한다. 같은 지점의 사진 10장에 가격표가 보이더라도 원본 가격표를 갱신하는 곳은 한 군데다.

| 범위 | 한 행에서 읽을 값과 출처 |
|---|---|
| 이미지 | 안정적인 사진 ID, 샵 ID, S3 버킷·객체 키, 인스타 원본 게시물 URL, 슬라이드, 보관 시각. RDS의 `catalog_portfolio_images`를 사용한다. 서명 URL은 조회 때 생성한다. |
| 작업 내용 | `catalog_portfolio_work_types`의 확인 시술(네일·헤어·메이크업), 공개용 세부 작업명, 내부 검토 근거. 공개 API에서는 확인된 시술명과 공개용 설명만 제공한다. |
| 지점 | `shops`의 상호, 도로명주소, 위도·경도, 전화번호. 공식 인스타 계정, 네이버 지도 URL, 네이버 플레이스 URL을 제공하고 네이버 예약 링크는 확인된 샵에만 제공한다. |
| 가격·리뷰 | 샵의 메뉴별 가격, 최저가, 리뷰 수와 리뷰 목록. 특정 사진의 시술 가격은 그 작업과 메뉴의 연결 근거가 생겼을 때만 별도 필드로 제공한다. 연락처나 가격을 모르면 비워 둔다. |

샵 연결 키는 `shop_id`다. 같은 이름이나 인스타 계정을 쓰는 다른 지점의 사진이 섞이지 않게 한다. 사진 식별자는 기존 이미지 기본 키인 `(shop_id, post_code, sha256)`에서 만들 수 있다. 후보 테이블 `catalog_portfolio_candidates`의 `selected` 판정과 시술 검토를 결합할 때는 **샵 ID·게시물 코드·슬라이드·해시**가 모두 일치해야 한다. 앱의 샵 상세에서 제외하는 지점과 운영 숨김 목록(`shop_suppressions`)은 피드에서도 제외한다. 메뉴·리뷰는 샵 단위 배열로 읽어 사진 행 수가 늘지 않게 한다.

처음에는 일반 뷰로 시작한다. 사진·가격·전화·숨김 상태가 바뀌면 다음 조회부터 반영된다. 실제 데이터에서 전체 피드와 샵별 피드의 쿼리 계획과 지연 시간을 측정한 뒤, 병목이 생기면 피드 정렬 부분만 물리화 뷰(MV)로 전환한다. 이때도 숨김 여부는 응답 직전에 확인한다.

## API와 앱 동선 제안

| 동작 | 계약 초안 |
|---|---|
| 포트폴리오 피드 | `GET /api/v1/portfolios`. 가벼운 사진 카드와 다음 커서를 반환한다. 시술 종류로 필터링한다. 최신순 정렬에서 시각이 같은 사진은 사진 ID로 순서를 정한다. |
| 사진 선택 | `GET /api/v1/portfolios/:id`. 선택 사진과 작업 설명, 샵 정보, 샵 기준 가격·리뷰를 제공한다. 목록에서는 상세 리뷰와 메뉴 전체를 반복 전송하지 않는다. |
| 같은 샵의 다른 작업 | `GET /api/v1/portfolios?shopId=…`. 선택 사진을 제외하고 동일 지점만 표시한다. 다른 사진이 0장이어도 샵 상세로 갈 수 있다. |
| 가게로 이동 | 소비자 앱의 기존 `/shop/[id]`로 이동한다. 전화·네이버 예약 등은 해당 샵에 확인된 경로를 사용한다. |
| 사진 열기 | `GET /api/v1/portfolios/:id/image`. 서버가 노출 가능한 사진인지 확인한 후 제한 시간 동안만 유효한 S3 URL로 연결한다. 목록 조회에는 S3 LIST·HEAD 호출이 필요 없다. |

## 사진이 없는 샵

수집 중에는 **미점검**, **접근 실패·지점 불명으로 재확인**, **점검 완료·확정 사진 0장**을 분리한다. 셋 모두 현재 피드에는 나타나지 않지만 다음 수집 대상과 정제 결과는 다르다. 운영 샵의 영구 삭제는 별도 결정이다. 수집 종료 후에도 0장인 샵만 후보로 세고, 파트너 관계와 예약·슬롯·리뷰·즐겨찾기 연결을 먼저 점검한다. 피드에서 숨기는 것만으로 제품 목적을 달성하면 원본 샵은 보존한다.

## S3 비용 관리 제안

2026-11-28 서울 리전에서 확정 인스타 사진 7,805장은 약 0.44GiB, 검수용 사본 11,320장은 약 0.68GiB였다. 당시 S3 Standard 첫 구간의 저장 단가로는 이 두 경로 합계의 **저장료만 월 약 0.03달러**다. 조회·전송·태그·세금은 별도이며 이 수치는 당시 규모를 설명하는 예시다. [S3 요금](https://aws.amazon.com/ko/s3/pricing/) · [서울 리전 단가표](https://pricing.us-east-1.amazonaws.com/offers/v1.0/aws/AmazonS3/current/ap-northeast-2/index.json)

1. 확정 이미지는 비공개 키 `catalog-portfolios/instagram/<shop_id>/<sha256>.jpg`에 보관한다. 같은 지점의 같은 파일은 재시도해도 한 번만 저장하고, 원본 게시물과 출처는 RDS에 보존한다.
2. 검수용 `catalog-portfolios/pending_review/instagram/`에는 검수 중·확정·탈락 사본이 섞여 있다. 확정 사본은 최종 객체와 RDS 연결을 확인하고, 탈락 사본은 재검토 기간을 정한 뒤 정리한다. 먼저 상태별 예상 삭제 건수·용량을 보고, 정리하기로 한 객체만 태그나 전용 경로로 구분해 만료한다. 미검토 사본에는 만료를 걸지 않는다.
3. 목록은 페이지 단위로 읽고 화면에 보이는 사진부터 로드한다. 현재 확정 사진은 평균 약 60KiB이므로 썸네일을 일괄 생성하기 전에 크기와 전송량을 비교한다. 반복 조회가 늘면 비공개 S3 앞에 CloudFront를 두고 캐시 적중률, 원본 GET 수, 사용자에게 전송한 바이트를 함께 본다. [CloudFront 요금](https://aws.amazon.com/ko/cloudfront/pricing/)

## 운영 전환 전에 확인할 것

- 다른 PC에서는 같은 상호의 두 지점, 사진 여러 장인 샵, 사진 한 장인 샵, 검수 대기·탈락 사진, 숨김 샵, 가격·전화가 비어 있는 샵을 로컬 테스트 데이터로 준비한다.
- 사진 한 장의 행이 메뉴·리뷰 수만큼 중복되지 않는지, 다음 페이지에 같은 사진이 다시 나오지 않는지, 모든 노출 카드가 같은 ID의 샵 상세로 이어지는지 확인한다.
- 기존 Mac에서 대상 수, 점검 완료·재시도·개별 검토 건수, 확정 이미지 수와 샵 수, S3·RDS 동기화 결과를 인계한다. 수집 중간 수치는 완료 판정 기준으로 사용하지 않는다.
- 사용자가 수집·정제 결과를 확인하고 전환을 요청하면 DB 조회 모델, API, 소비자 앱 순으로 적용한다. 샵 삭제와 S3 만료 정책은 대상과 영향을 따로 확인한 뒤 결정한다.
