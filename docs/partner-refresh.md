# 파트너샵 전용 갱신

`partner-sync` Actions는 매번 백엔드의 현재 `is_partner=true` 목록을 50곳씩 페이지 조회한다. 매장 ID를 코드에 고정하지 않는다. 등록하면 다음 실행부터 대상이 되고, 해제하면 조회·저장 단계 모두 제외된다.

| 데이터 | 실행/갱신 기준 |
|---|---|
| 예약 가능 시간 | 매시 3·8·13…58분 실행, 마지막 성공 이후 3분 이상이면 조회. 오늘부터 3일 |
| 이벤트 | 같은 fast 실행에서 마지막 성공 이후 30분 이상일 때 |
| 상세·사진·리뷰·메뉴 | 매시 11분 실행, 마지막 성공 이후 6시간 이상일 때 |

Actions 예약 실행은 지연될 수 있다. 공식 실시간 API나 웹훅 연동이 아닌 주기적 조회다. 기존 데이터 접근의 허용 범위를 확대하는 변경은 아니다.

## 저장과 정리

- `GET /internal/shops/partner-targets?kind=slots|events|details&after=<id>`: 최대 50곳과 다음 커서. 내부 키 인증 필요.
- `POST /internal/shops/partner-refresh`: `{id, kind, observedAt, data}`. 현재 파트너 여부를 트랜잭션의 행 잠금 아래 다시 확인한다.
- 각 소스의 관측 시각을 `detail._partnerRefresh`에 기록한다. 뒤늦게 끝난 과거 작업은 최신 결과를 덮어쓰지 않는다.
- 예약: 모든 담당자 조회가 성공한 샵만 해당 날짜창의 scraper 슬롯을 최신 상태로 맞춘다. 같은 슬롯은 유지하고 사라진 슬롯 삭제·신규 슬롯 추가만 하여 DB 쓰기량을 줄인다. 실제 빈 배열은 마감으로 반영하며, 오류·데이터 누락은 이전값을 보존한다. 과거 scraper 슬롯은 삭제한다. owner 슬롯은 보존한다.
- 이벤트: 정상 페이지에서 이벤트 없음이 확인되면 이전 이벤트를 null로 정리한다. 실패한 페이지는 이전값을 보존한다.
- 사진·리뷰: 배열에 누적하지 않고 최신 샘플로 교체한다. 리뷰 최대 15개, 사진 섹션별 최대 12개(리뷰 사진 30개), 중복 URL 제거. 수집기 읽기 모델은 이보다 작은 기존 제한도 유지한다. 확인할 수 없는 사진/리뷰 섹션은 보존한다.
- 브라우저 컨텍스트는 매장마다 닫는다. 전체 매장/사진 스냅샷 파일을 저장하지 않으며, 페이지 단위로 처리한다.
- 커밋 후 해당 상세 및 목록·슬롯 캐시를 삭제한다. Redis는 SCAN/UNLINK, 메모리 캐시는 기존 LRU 상한을 유지한다. TTL은 캐시 장애 시 보조 수단이다.
- 전용 갱신이 한 번 성공한 파트너는 기존 전국 수집의 해당 데이터 갱신에서 제외한다. 파트너 해제 후에는 일반 수집 대상으로 돌아간다.
- 첫 예약 동기화는 알림 기준선으로 사용한다. 이후 신규 빈자리만 기존 알림 경로로 전달하며, 한 날짜에 8개를 초과한 대량 신규 슬롯 알림은 생략한다.

## 실행과 확인

수동 실행: `gh workflow run partners.yml --repo themuselab/syak -f mode=fast` 또는 `-f mode=details`.

검증: `cd scraper && python -m unittest test_partner_refresh.py`; 백엔드 `PartnerRefreshService.test.ts` 및 전체 Jest 테스트. 신규 API를 백엔드에 먼저 배포한 뒤 workflow를 반영한다. fast 기본 예산 210초, details 600초. 실패가 있으면 Actions를 실패 처리하고 이전 데이터는 남긴다.

데이터 교체는 DB 행을 정리하는 것이며 PostgreSQL 파일 크기를 즉시 줄이는 작업은 아니다. `VACUUM FULL`이나 예약/고객 기록 삭제는 수행하지 않는다.
